# 刪除家長是硬刪、不留紀錄，兩種後台成員都能刪

後台原本沒有任何刪除功能：列表裡的測試帳號（小明、仔仔）與「未填姓名」的空帳號只能由人直接下 SQL 清掉，而家長端的條款（`LegalTerms.tsx`「刪除權」）承諾「申請刪除兒童檔案及全部關聯資料，收到申請後於合理期限內完成刪除並反饋」——承諾了，卻沒有工具。客戶 2026-09-11 提出要一顆刪除鍵。本次 grilling 定案如下。

## 決定

- **硬刪。** 直接刪掉 `users` 那一列，外鍵連帶刪掉孩子檔案、篩查結果、報告、掃碼連結、解鎖權益。不加 `deleted_at`。
- **兩種後台成員都能刪**，範圍就是各自的視野：公司成員只刪得到自己公司的家長，全域管理員刪當下切到的視野裡的家長（未歸屬的家長因此只有全域管理員刪得到）。跨公司的請求回 **404**，與詳情路由一致——403 等於承認那個 id 存在。
- **有付款紀錄的家長不能刪**，回 409（`HAS_PAYMENTS`）並在畫面說明。
- **預約在同一個交易裡先刪。** 外鍵預設只把 `expert_bookings.user_id` 清空，會留下一筆後台永遠找不到、卻含姓名與手機的孤兒列。
- **不建刪除紀錄表。**
- **確認框**要求輸入手機尾號四碼（沒有手機的舊信箱帳號輸入信箱），並列出會刪掉什麼；進行中的預約（`new`／`contacted`／`scheduled`）特別標出。
- **被刪的家長若手機上還登入著**，同步端點找不到帳號時回 401「請重新登入」，重新登入即新帳號。

## 為什麼是硬刪而不是軟刪

條款承諾的是「刪除」，不是「隱藏」。軟刪還有兩個實際的麻煩：後台每一句查詢與家長登入都要多一個「排除已刪除」的條件；`uk_company_phone` 唯一索引會讓被軟刪的手機號再也註冊不了，除非再加特例。硬刪反而有現成的護欄——`test/adminScope.structure.test.ts` 逐句檢查 `adminStore.ts` 的 SQL 有沒有帶公司條件，DELETE 寫在那裡就自動受保護。

## 為什麼不留紀錄

產品端 2026-09-11 的決定：「刪了就刪了。」代價已說明並接受——兩年後有人問「你們當時刪了嗎」，系統答不出來；哪家合作公司的誰刪了誰，森心康看不到。伺服器日誌照既有慣例留一行，但那不是長期保存的紀錄。

## 為什麼公司成員也能刪

`deploy/schema.sql` 的註解寫著孩子的健康資料**掌管方是森心康，不是合作公司**，所以「只有全域管理員能刪」本來是預設答案。改成公司成員也能刪，是為了讓家長向合作公司提出刪除申請時，流程不必轉一手到森心康。這是刻意的偏離，不是漏了角色檢查。

## 為什麼擋付款

付款紀錄是對帳憑證，退款與客訴都要它。實際上只有專案 A 有付款、只有專案 B 有公司成員，所以這道擋門與公司成員永遠碰不到面——程式碼兩道都做，不因為現實中碰不到就省掉。

## 後果

- **掃碼帶走的報告連結從此 404。** 那條連結原本永久有效、沒有撤回手段（`report_links` 的註解），刪除家長成了唯一的撤回方法。
- **同一支手機刪掉後可以重新註冊。** 唯一索引隨那一列消失，`sms_codes` 沒有外鍵。清測試帳號時這正是要的。
- **付過錢的家長提出刪除申請，目前沒有路。** 條款承諾刪除，擋門擋的是付款憑證；能走的只剩匿名化（留付款紀錄、洗掉手機與孩子資料）或人手動處理。這是已知缺口，本次不做匿名化。
- 結構測試的範圍表要加進 `payments`：擋門那句 COUNT 必須 JOIN `users` 帶公司條件。

## 刻意不做

只刪一份報告而保留家長、列表層級的批次刪除、「尚未篩查」的列表篩選器、匿名化。
