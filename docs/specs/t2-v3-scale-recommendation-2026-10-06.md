# T2 v3：量表推薦引擎

> **給接手實作的人**：客戶這份規格書已經是寫給 IT 的（輸入、演算法、偽代碼、30 格標準表、10 個案例、驗收清單、JSON 設定都有），
> **本文件不重抄演算法**，只寫：權威怎麼排、怎麼接到我們的資料、跟現行衝突的地方、沒有治療師時怎麼辦、暫採、票。
> 引用客戶規格書一律寫「客規 §N」。
>
> **權威**：使用者 2026-10-07「依新檔案優先」。這份規格書推翻了兩個既有決定：2026-09-24「購買後每一維度只測一支」（暫行題量）
> 與 2026-09-29「拿掉診斷方向」。兩者都以客規為準。

## 0. 一頁結論

客規要的是：T1 做完，依 **T1 九維等級＋逐題關鍵題＋診斷（0–2 個）＋年齡＋填寫人＋近 3 個月做過的** 推 **3–5 份** T2 問卷
（31 支工具裡的 24 支家長可填的），附理由、時間（家長端 ≤ 90 分鐘、分兩次）、P0 安全／醫療提示、聽力前置、缺口說明、
0–3 份 T3 當面評估預告。T1 全正常又沒有診斷 → 不推，3–6 個月後複篩。

接進來要四件事，前三件互不依賴：

1. **T1 要多存東西**：逐題作答（現在只存每維總分與三級狀態）、診斷、上園／上學、抽動、聽力檢查、孕週（早產矫正，客規 §3 要但沒列進「新增 4 欄」）。
2. **引擎本身**：純函式＋客規附錄 A 的設定＋客規 §11（30 格）、§12（10 例）、§14（V1–V13）全部當測試。這一步不碰題庫、不碰畫面。
3. **題庫換成完整版 31 支**（9/23 那包）：我們現在是 9/08 的 22 支，工具 id、題目、計分、分級都要換。這是最大的一塊，**另寫一份規格**（§6）。
4. **接上**：`GET /api/t2/plan` 改回引擎的輸出、T2 入口畫面照客規 §13.2 的樣子列。要等 1、2，以及 3 至少把被推薦到的工具接進來。

### 2.2 T1 等級（客規 §1）

客規每題 0＝可以做到、2＝還不能，每維得分 `8 − Σ`。A 的每題 2＝可以做到、0＝還不能，每維 `Σ`。**兩者數值相同**，不用換算。

| 分數 | 客規等級 |
|---|---|
| 8–7 | 0 未見明顯 |
| 6–5 | 1 輕度 |
| 4–3 | 2 中度 |
| 2–0 | 3 明顯 |

紅旗題答「还不能」（A 的 0 分）→ 該維至少 2。**只算「还不能」**；A 的 T1 報告把「有时」也算紅旗問題（`val < 2` → 臨界），那是報告的事，不動。

> ⚠️ 同一個 0–8 分現在有三種讀法：A 的 T1 報告（8 正常／6–7 臨界／≤5 遲緩）、這裡（7–8 未見明顯）、線上干預的 T1 推定（只有 8 是綠）。
> 照「新檔案優先」三者各管各的，各寫各的函式，不要共用 —— 合併是客戶要決定的事（§7 第 1 題）。

### 2.3 逐題作答的保存

- T1 交卷時多存一份 `items: Record<題 id, 0|1|2>`（A 的計分方向），跟每維分數放同一筆。
- 引擎要的「組＋維度＋題序」由題 id 對回 `t1Data.ts`（`t1_a_13` → A 組、注意力、第 1 題）。客規 §8 的關鍵題表寫成常數，**每一條都要有測試證明它指到的題目文字跟客規一字不差**（客規題序從 1 起）。
- **舊的 T1 沒有逐題資料**：`rfdims`、關鍵題標籤都當沒有；推薦結果加一條提示「T1 逐题资料缺，重新做一次 T1 推荐会更准」（**暫採**）。

## 3. 引擎

- `src/t2/recommend/`：`recommendT2(input, config) → Recommendation`，純函式。形狀照客規 §13.1（`status`、`alerts`、`dimQueue`、`tools`、`t3`、`gaps`、`parentMinutes`、`overrides`）。
- 設定：客規附錄 A 的 JSON 寫成 `src/t2/recommend/config.ts`。**由腳本從 docx 抽出**（`scripts/t2-extract-recommend-config.ts`，`--check` 比對），跟題庫一樣不手改 —— 客戶改了規格書就重抽。
- 客規 §10 說有一份約 150 行的 Python 參考實作，我們沒有 → **跟客戶要**；拿到之後放 `docs/reference/`，測試多一層「同輸入兩邊結果相同」。
- 測試：
  - 客規 §11 的 30 格（6 診斷 × 5 年齡）逐格比對（量表、順序、分鐘、T3、提示）。
  - 客規 §12 的 10 個案例逐例比對。
  - 客規 §14 的 V3–V13 寫成性質測試，窮舉 12–216 個月 × 等級組合 × 診斷組合抽樣。
  - 客規的表若跟它自己的演算法算出來不一樣（偶有），**以表為準還是以演算法為準**要問；測試先釘表，不一致的列在勘誤檔。
- 參數（客規 §9.4）先寫成常數；客規說「放在后台设定」，後台頁面等需要再做（§7 第 6 題）。

## 5. 家長端畫面（T2 入口）

照客規 §13.2 的模板：標題、每一份（名稱、針對哪個維度、為什麼、誰填、幾分鐘）、合計時間與「建议分 2 次」、缺口、`NO_T2`（T3 不出）。

- 模板裡的「中度落后／轻度落后」踩《用语对照表》的「落后」。照 memory `parent-wording-apply-all-tiers`：**模板是框架字、不是客戶的內容原文**，照對照表換掉（**暫採**換成既有 `statusWording` 的說法），並列進 §7 讓客戶知道。
- 量表名稱是客戶給的專有名詞，照用。
- 「第一次填写」「第二次填写」分組顯示。
- `NO_T2` 時入口不出現，T1 報告上寫「目前不需要第二层检查，建议 3–6 个月后再做一次 T1」（取代現在 `entrance` 的「none」狀態那一句）。
- 付費牆：`/api/t2/plan` 仍在白名單（付費前要看得到推薦）。客規 §15 第 6 題建議「按套餐一价」—— 現在 `PAYWALL_FREE`，不影響。

## 6. 題庫換版（另一份規格）

引擎推的是客規代碼（`SXK-ASQ3`、`SXK-LQ`……），家長要能真的填。完整版 31 支（`NEWT2/森心康评估工具包_完整版_20260923.zip`）跟現在 22 支的差異已記在 memory `t2-kit-full-edition-2026-09-24`（DEV、WARN 不見，SP 拆兩支，氣質合一，新增 LQ／PLC／EMO／QOL／TIC 等）。

這塊要寫成獨立規格 `t2-v3-toolkit-full-edition`，至少回答：

1. 抽取：31 支的資料常數怎麼讀（沿用「只在沙箱求值資料宣告」的做法）、哪三套分級取哪一套。
2. 判定：每支工具的分級怎麼變成**每個主維度的 0–3**（線上干預的推送說明也吃「T2 分级 0/1/2/3」）。客規只定「主維度＝選入後即視為已覆蓋」，沒定怎麼判 —— **要問客戶**。
3. 報告（`findings.ts`）：維度判定從「星號工具」改成「客規主維度」；同一維度兩支（深度）時取重的還是取主量表的。
4. 舊作答（`kit-20260908` 的 `t2_tool_results`）與舊快照怎麼相容。

在那份規格完成之前，§3 的引擎可以先做、先測，但 §5 的入口不能上線（會推出家長填不了的工具）。**暫採的過渡**：引擎推出來的工具若題庫裡還沒有，入口那一份顯示「即将开放」、不計入時間 —— 只有在使用者要先上線入口時才用。
