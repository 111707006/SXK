# 專案 B 以單一部署服務多家合作公司

專案 B 原本設計成交付給**一家**合作公司（`t1.sxkscreen.com`，一個部署、一個資料庫）。要服務多家之後，我們決定**不複製部署**，改為同一套部署 + 資料層以 `users.company_id` 區隔；家長的歸屬由進站連結的參數決定並綁在帳號上，而非由網址決定。

## 考慮過的選項

**每家公司一個部署**（延伸現有 `APP_MODE` 的作法）與**每家公司一個資料庫**都被否決，理由是實測證據而非偏好：專案 B 講了一個多月，`t1.sxkscreen.com` 至今在 DNS 上不存在；`deploy/schema.sql` 一次都沒套用到線上資料庫。**一個部署都還沒完整跑起來，N 個部署只會是 N 倍的沒跑起來。** 單庫另外讓森心康的跨公司檢視是一句 `GROUP BY`，而非 N 次查詢再自行合併。

**以子網域決定歸屬**（`a.sxkscreen.com`）被否決：子網域是歸屬手段而非隔離手段，而每加一家就要 DNS + nginx + 部署設定；微信支付的 H5 域名上限為 5 個且子網域各算一個，第 6 家公司會撞牆。改用連結參數的代價是歸屬只能綁在裝置或帳號上，因此**家長必須註冊**——這推翻了「專案 B 暫定不登入」的暫行決議（見 `與客戶討論的問題.md` 第五項）。

## 一併決定的事

- **權限只有兩種角色**：全域管理員（森心康）與公司成員。公司無法自行增刪員工帳號，由森心康代為處理；當這件事開始煩人，就是升級成三種角色的訊號。
- **全域管理員必須明確切換到某一家公司，且切換留下紀錄。** 若「看得到所有公司」是日常狀態，誤看永遠不會被發現。
- **專家與客服由各家公司自備。** 這推翻了「專案 B 沿用現有三位森心康專家」（同上文件第六項），並使專家從寫死的常數變成資料。
- **家長端維持統一的中性品牌**，不做各公司品牌。品牌目前由 `VITE_APP_MODE` 在建置期選定並被樹搖（見 `scripts/check-brand.mjs`）；改為各公司一套必須移到執行期解析，與現行架構方向相反，等有公司真的要求再做。

## 後果

**單庫的代價是漏一個 `WHERE` 就跨公司外洩。** 這與 2026-07-31 修掉的付費閘門授權繞過是**完全相同的失敗形狀**——檢查的欄位與實際回應的內容不是同一個——只是炸開的範圍從 ¥19.9 變成別家公司的孩子的健康資料。因此隔離必須做成**單一入口的資料層**，不允許任何地方直接下 SQL，讓「有沒有帶公司條件」成為可被測試釘住的事實。

⛔ **合作公司看得到家長與孩子的完整資料（含九維分數與 AI 報告全文），而系統沒有任何同意機制。** 依《個人信息保護法》這屬於向第三方提供個人信息，需單獨同意，兒童另需監護人同意；隱私條款已對外承諾這幾件事卻未實作（`與客戶討論的問題.md` 第三項）。經產品端決定**延後處理**，但這是**上線的法律前提，不是待辦功能**。
